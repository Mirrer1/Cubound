# Cubound 작업 이력

> 만든 순서대로의 작업 이력. 자동으로 읽히지 않는 참고 문서라 기존 기능을 고치기 전에 해당 항목을 찾아본다. 새 항목은 맨 뒤에 쌓는다.

**기획.** 작은 큐브가 칸을 하나씩 건너 구멍을 찾아가는 아이소메트릭 퍼즐로 정했다. 규칙, 오브젝트, 스테이지 구성, 보스는 `docs/PRD.md`, 구조와 게임 모델은 `docs/ARCHITECTURE.md`, 디자인 방향은 `docs/DESIGN_BRIEF.md`에 정리했다. Bloxorz와 달리 큐브 모양을 1×1×1로 고정하고, 재미를 높이 차이와 오브젝트 조합에서 만들기로 했다. 게임 오버 대신 재시작만 두고, 보스마다 고유 제약을 주며 1월드 보스는 이동 횟수 제한으로 정했다. 능력이 있는 유료 큐브는 퍼즐과 별점을 망가뜨려서 기각했다.

**초기 세팅.** Vite 8, React 19, TypeScript strict, Tailwind v4, Zustand, Motion, Vitest로 pnpm 워크스페이스 모노레포를 만들었다. 게임은 `apps/web`, 나중의 NestJS 서버는 `apps/server`, 공유 코드는 `packages/`에 둔다. 의존성은 각 앱에 두고, 공유 버전은 `pnpm-workspace.yaml`의 `catalog`, 공통 TypeScript 설정은 `tsconfig.base.json`으로 관리한다. 운영비 0원을 위해 서버와 DB 없이 정적 배포로 시작한다. 곁가지: Node 22.11에서 Vite 8의 네이티브 모듈이 설치되지 않아 Node 24로 올렸다.

**작업 규칙.** 이전 프로젝트의 규칙을 가져와 `.claude/rules/code/`(공통, 컴포넌트, 게임 로직, 테스트)와 `/update-docs` 스킬을 만들었다. Next.js, DB, 외부 API 규칙은 이 프로젝트에 해당하지 않아 뺐고, 게임 로직 순수성 규칙을 새로 넣었다. Prettier와 import 정렬, Tailwind 클래스 정렬, `@/` 경로 별칭을 추가했다. 곁가지: git 저장소를 만들고 Husky와 lint-staged로 커밋 전 자동 검사를 붙였다. Windows의 `core.autocrlf`와 Prettier 줄바꿈이 충돌하지 않게 `.gitattributes`로 LF를 고정했다.

**디자인.** `docs/DESIGN_BRIEF.md`를 Claude Design에 전달해 데스크톱과 모바일의 타이틀, 스테이지 선택, 게임, 클리어, 보스 안내, 보스 게임 화면과 오브젝트 상태별 스타일, 넓은 맵, 클리어 연출 콘셉트를 받았고 `docs/design/`에 원본을 두었다. 진한 테두리 선 버전은 딱딱해서 면 명암만 쓰는 부드러운 버전으로 되돌렸고, 칸 경계는 체크무늬 미세 톤 차이로 표현한다. 색 토큰, 글꼴, 아이소메트릭 치수를 `docs/ARCHITECTURE.md` "디자인 기준값"에 옮기고 `index.css` 토큰을 맞췄다 (바닥 왼쪽과 오른쪽 면 색이 뒤바뀌어 있던 것 수정). 프로토타입의 이동 로직은 PRD와 달라 참고하지 않는다. 곁가지: 방향 버튼 없이 웹은 키보드와 `R` 재시작, 모바일은 스와이프만 쓰고, 1월드는 새 요소가 처음 나올 때 한 줄 가이드를 띄운다. 스테이지는 화면을 넘는 넓은 필드를 구역 카메라로 보여주고, 큐브는 모서리를 축으로 굴러가며, 별점은 월드 보스 제약을 따르고 기본은 이동 수다. 작은 라벨은 영어 대문자, 버튼과 문장은 한글로 정했다.

**기본 이동 규칙.** 큐브가 방향키 방향으로 한 칸 이동하고, 필드 밖과 바닥 없는 칸과 높은 칸으로는 막히며, 낮은 칸으로는 몇 층이든 내려가고, 목표 칸에 도착하면 클리어한다. `game/rules.ts`의 `move`가 새 상태와 연출용 이벤트(`moved`, `fell`, `blocked`, `cleared`)를 돌려주는 순수 함수이고 타입은 `game/types.ts`에 있다. 타입에는 지금 쓰는 필드만 두고 오브젝트, 보스 제약, 가이드, 구역은 해당 기능을 만들 때 추가한다.

**필드 화면과 키보드 조작.** 게임 화면에 아이소메트릭 필드와 큐브를 그리고 방향키로 이동, `R`과 재시작 버튼으로 처음부터 한다. 좌표 변환과 블록 면 계산은 `game/iso.ts`, 그리기는 `components/board/Board.tsx`, 상태는 Zustand `store/gameStore.ts`, 키 매핑은 `platform/input.ts`에 있다. 면 명암은 CSS `color-mix`로 색 토큰에서 바로 만들어 16진수 색을 코드에 두지 않았다. 스테이지 `stages/world-1/01.json`은 도구 없이 내려가기만으로 풀리는 임시 맵이고 스테이지 제작 단계에서 교체한다. 이동 애니메이션은 아직 없고 구르기 단계에서 넣는다. 곁가지: Jost와 IBM Plex Mono 글꼴 연결.

**상자.** 상자 쪽으로 이동하면 먼저 밀고, 밀 수 없으면 상자 위로 한 층 올라간다. 낮은 칸으로 밀면 떨어지고, 바닥 없는 칸으로 밀면 밀던 높이의 바닥으로 메워져 다리가 된다. `game/rules.ts`의 `pushBox`가 처리하고 `pushed`와 `climbed` 이벤트를 돌려주며, 상자와 메운 칸 때문에 `GameState`에 `boxes`와 `heights`를 두었다. PRD에 없던 "밀 수 없으면 올라가기"와 "메운 높이"는 계단과 다리로 쓰기 위해 정했다. 메운 칸은 옐로 윗면으로 그린다. 곁가지: 임시 스테이지를 상자 오르기와 메우기를 모두 쓰는 맵으로 바꿨다.

**스위치와 문.** 큐브나 상자가 스위치 위에 있는 동안 연결된 문이 열린다. 닫힌 문은 지나갈 수도 올라설 수도 없고 상자도 밀어 넣을 수 없으며, 문 위에 무언가 있으면 스위치가 풀려도 닫히지 않는다. 문 상태는 따로 저장하지 않고 `game/rules.ts`의 `isDoorOpen`이 매번 계산하며, 이동 전후로 바뀐 문은 `door` 이벤트로 알린다. 스테이지 데이터는 `entities`에 `switch`(target)와 `door`(id)로 연결한다. 곁가지: 문 색 토큰 `door` 추가, 임시 스테이지에 스위치와 문 추가.

**사다리.** 방향키만으로 다룬다. 빈손으로 사다리 칸에 들어가면 줍고, 들고 한 층 높은 칸 쪽으로 가면 제자리에서 기대 놓고, 한 번 더 가면 오르며, 빈손으로 타고 내려오면 다시 든다. 놓은 사다리가 남아서 재사용하려면 돌아가야 하는 퍼즐이 생긴다. `game/rules.ts`의 `arrive`가 줍기를, `climbOrPlaceLadder`가 놓기와 오르기를 처리하고 `pickedUp`, `placed`, `climbed`(via) 이벤트를 돌려준다. 그리기는 `components/board/BoardLadder.tsx`로 바닥, 기댄, 든 상태를 선으로 그린다. 곁가지: `iso.ts`에 칸 단위 이동량 `isoDelta` 추가, 임시 스테이지에 사다리 구간 추가.

**브라우저 테스트.** Playwright를 넣어 `pnpm e2e`로 화면이 뜨고 조작되는지 확인하고, `pnpm shot`으로 상태별 화면을 캡처해 Claude가 직접 보고 확인한다. 사용자의 로컬 확인은 움직임의 느낌과 재미로 줄였다. 첫 캡처에서 두 버그를 잡았다. Tailwind v4가 코드에서 문자열로 조합한 색 변수(`player`)를 빼버려 큐브가 검게 나와 `@theme static`으로 모든 토큰을 남기게 했고, 화면 높이가 제한되지 않아 필드 아래가 잘려 `h-dvh`로 고정했다.

**풀이 검사기.** `game/solver.ts`의 `solve`가 게임과 같은 `move`로 너비 우선 탐색을 돌려 최소 이동 수와 경로를 구하고, `moveLimit`(최소 + 20% 올림)과 `stars`로 별과 보스 제한을 계산한다. `stages/stages.test.ts`가 모든 스테이지 JSON이 풀리는지 자동으로 검사해서, 규칙을 바꿔 스테이지가 막히면 테스트가 실패한다. 문 상태는 다른 상태로 계산되어 탐색 키에서 뺐다. 임시 스테이지 탐색이 약 0.8초라 넓은 맵에서 느려지면 최적화한다.

**화면과 진행 저장.** 타이틀, 스테이지 선택, 게임, 클리어 카드를 만들고 화면 전환과 카드 등장에 Motion 페이드를 넣었다. 화면 상태는 Zustand `screen`으로 바꾸고 라우터는 두지 않았다. 진행은 `game/progress.ts`의 순수 함수(`recordClear`는 더 좋은 기록만 갱신, `isUnlocked`는 앞 스테이지 클리어 시 열림)로 계산해 `platform/storage.ts`로 localStorage에 저장한다. 스테이지 목록은 `stages/index.ts`가 JSON을 모아 만들고, 최소 이동 수는 열 때마다 탐색하면 느려 JSON의 `best`에 두고 `stages.test.ts`가 풀이 검사기 결과와 같은지 검사한다. 모바일은 조작 버튼을 하단으로, 스테이지 카드를 2열로, 클리어 카드를 하단 시트로 바꿨다. 곁가지: 색 토큰 `surface`, `locked`, `faint` 추가. 타이틀 장식의 반투명이 사각 테두리를 남겨 배경색 섞기로 바꿨고, 스크린샷 스크립트를 타이틀부터 모바일까지 넓혔다.

**연출.** 큐브가 이동 방향으로 굴러가고, 막히면 기울었다 돌아오며, 내려갈 때는 칸 끝을 넘은 뒤 떨어진다. 상자는 미끄러지거나 떨어지고, 스위치와 문은 높이가 부드럽게 바뀌고, 사다리는 페이드로 나타나고 사라진다. 게임 규칙은 즉시 계산하고 화면만 이전 상태에서 보간하는 방식이라, 위치 계산을 `components/board/frame.ts`의 순수 함수로 두고 테스트했다. 구르는 큐브는 `cube.ts`가 3D 회전 후 투영한다. 연출 중 입력은 1개까지 기억해 이어 실행한다. 클리어는 구멍으로 가라앉는 큐브와 빛 고리, 조각 연출 뒤에 카드가 나온다. 구역 카메라(`game/camera.ts`, `useCamera`)가 큐브가 들어선 구역으로 부드럽게 옮겨가고, 가림 처리(`game/occlusion.ts`)가 큐브를 가리는 앞 칸을 반투명하게 한다. 곁가지: 캡처에서 목표 칸을 투명하게 할 때 구멍 장식만 남는 문제와 기댄 사다리 때문에 칸이 계속 투명한 문제를 고쳤다. 사다리는 끝이 높은 칸 위로 살짝 솟게 했다. 이동 수 숫자 전환 연출과 모바일에서 넓은 구역 따라가기는 아직 없다. 든 사다리는 작아 보여서 바닥에 놓인 크기 그대로 큐브 위에 올린다. 페이지 바깥 스크롤을 막고, 안쪽 스크롤 영역은 `scroll-area` 유틸리티(얇은 모노톤 스크롤바, 자리 미리 확보)로 스크롤바가 생길 때 레이아웃이 밀리지 않게 했다.

**연출 부드럽게.** CPU를 4배 느리게 한 측정에서 상자 밀기 중 39프레임 중 17프레임이 끊겼다(평균 28.6ms). 연출 중 매 프레임 맵 전체 칸을 다시 그리던 게 원인이라, 칸을 `components/board/BoardCell.tsx`(React.memo)로 나눠 값이 안 바뀐 칸은 건너뛰게 했다. 같은 조건에서 평균 17.5ms, 끊김 2프레임으로 줄었다. 연출 시간도 급하게 느껴져 0.18초 안팎에서 0.24~0.32초로 늘렸다. 호버와 누름 전환은 `transition-soft`(색 0.2초, 누름 크기 0.12초, 처음과 끝이 느린 곡선) 유틸리티로 통일했고, 스테이지 카드는 밝기 필터가 전환에서 빠져 뚝 바뀌던 것을 그림자와 테두리 전환으로 바꿨다. 처음엔 감속 곡선이라 0.1초 만에 60%가 바뀌어 툭툭 끊겨 보여서, 처음과 끝이 모두 느린 곡선(cubic-bezier(0.37, 0, 0.63, 1))으로 바꿔 전환 시간에 고르게 퍼지게 했다. 스크롤바는 브라우저 기본 호버 색이 진해서 webkit 스크롤바 스타일로 평소 `line`, 호버 `line-strong`을 직접 정하고 위아래 여백을 줘 카드 둥근 모서리에 닿지 않게 했다. 파이어폭스는 표준 속성으로 같은 연한 색을 쓴다. 호버 색이 요소마다 달라(버튼은 배경, 카드는 그림자와 테두리) `hover` 토큰을 만들고 밝은 면은 모두 이 배경색, 진한 면은 `ink/90`으로 통일했다. 스크롤바 호버 색 변화는 브라우저가 전환을 지원하지 않아 툭 바뀌어서 없앴고, 호버 배경은 더 연하게(`#EBE9E5`) 조정했다.

**빠른 입력 반응.** 연출 중에는 입력을 1개만 기억해서 빠르게 누르면 나머지가 버려졌다(0.08초 간격 6번 중 3번만 반영). 처음엔 대기열을 2개로 늘리고 입력이 기다리면 2.5배로 빨리 재생했는데, 보통 속도로 눌러도 거의 매번 빨리감기가 켜지고 도중에 속도가 확 바뀌어 부자연스러웠다. 그래서 따라잡기는 입력이 2개 밀렸을 때만 1.3배로 서서히 올리고, 대신 연달아 누를 때 칸 사이에서 멈추지 않고 이어 굴러가게(`frame.ts`의 `moveEase`, `Chain`) 바꿨다. 0.2초 간격으로 누르면 6번 모두 바로 반영되고, 0.08초 연타는 한도를 넘는 입력을 버려 손을 뗀 뒤 밀리지 않는다.

**가이드 방식 결정.** 1월드 가이드를 플레이 중 말풍선에서 시작 전 스포트라이트형 스텝 가이드로 바꿨다. 1, 2, 3, 6, 9, 10스테이지에서 화면을 어둡게 하고 대상만 비추며 `>`, `Enter`, `Space`, 탭으로 1~3단계를 넘긴다. 말풍선은 무심코 움직이다 놓치기 쉬워서 기각했다. 읽고 끝나지 않게 시작하자마자 설명한 행동을 해보는 맵으로 보완한다. 문서만 고쳤고 구현은 아직이다.

**유저 맵 아이디어 메모.** 유저가 맵을 만들어 직접 플레이하고, 링크로 친구와 공유하고, 좋은 맵은 제작자에게 추천하는 기능을 PRD "이후 확장"에 4단계로 정리했다. 링크 주소에 맵을 담으면 서버 없이 공유할 수 있고, 풀이 검사기와 클리어 인증으로 못 푸는 맵을 막는다. 구현은 1월드 완성 뒤로 미뤘다.

**데이터 형식 고정.** 나중에 로그인과 유저 맵 공유를 붙이기 쉽게 스테이지를 만들기 전에 형식을 정했다. 스테이지 JSON에 `version: 1`을 넣고 `game/validate.ts`의 `validateStage`가 높이 맵, 시작과 목표, 오브젝트 위치와 겹침, 스위치와 문 연결, `best`, 구역을 검사한다. 모든 스테이지가 검사를 통과하는지 `stages.test.ts`가 확인하고, 유저 맵도 같은 함수로 거를 수 있다. 진행 기록에도 `version`을 넣고 `migrateProgress`가 버전 없는 예전 기록을 옮기며 깨진 기록은 걸러낸다. 서버와 인증은 커뮤니티 단계까지 필요 없어 붙이지 않았다.

**문서 점검과 인증 계획.** 커밋 전에 문서 전체를 코드와 맞춰 봤다. ARCHITECTURE의 폴더 구조를 실제 파일로 바꾸고, `move` 반환형, 스테이지 JSON 예시(없는 `size` 제거, `best` 추가), 빠진 색 토큰, 연출 설명을 고쳤다. PRD의 없는 "발판"과 보스 안내 방식, 컴포넌트 규칙의 색 칠하기와 연출 방식, 없는 `BoardTile` 예시를 바로잡았다. 서버와 인증은 ARCHITECTURE "서버와 인증 (나중에)"에 붙이는 시점(커뮤니티, 랭킹, 클라우드 저장, 결제), 방식(Supabase 우선, 서버 로직이 늘면 NestJS가 Supabase 토큰 검증), 권한 표, 기기 기록 합치기, 서버에서 경로를 다시 돌려 기록을 검증하는 계획으로 정리했다.

**스텝 가이드.** 가이드가 있고 클리어하지 않은 스테이지에 들어가면 화면을 어둡게 하고 대상만 비추는 설명 카드가 뜬다. `>`, `Enter`, `Space`, 화면 탭으로 넘기고 마지막 단계는 "시작"으로 끝내며, 카드 구석의 "건너뛰기"로 바로 닫는다. 대상 칸이 다른 구역이면 카메라가 따라가고 끝나면 큐브 구역으로 돌아온다. 게임 화면의 `?` 버튼(데스크톱 헤더, 모바일 하단)으로 다시 본다. 스테이지 JSON의 `guides`(문구 `id`와 칸 좌표나 `restart`, `moves`)를 `validateStage`가 검사하고, 문구는 웹과 모바일이 달라 `components/guide/guideTexts.ts`에 두고 터치 기기(`pointer: coarse`)면 모바일 문구를 쓴다. 띄울지 판단은 진행 기록 형식을 바꾸지 않고 기록 유무로 하는 `game/progress.ts`의 `shouldShowGuide`다. 가이드 중 입력은 스토어의 `move`와 `restart`에서 막아 나중의 스와이프에도 그대로 적용되게 했다. 대상 위치는 카메라 viewBox를 따로 계산하지 않고 `Board`가 그린 투명 사각형과 화면 요소의 실제 위치를 매 프레임 재서, 카메라 이동과 화면 크기 변화에도 어긋나지 않는다. 처음엔 대상이 화면 아래쪽이면 카드를 위에 뒀는데 낮은 창에서 목표 구멍을 가려서, 대상 위아래 중 빈 공간이 넓은 쪽에 두게 바꿨다. 임시 맵에는 확인용 2단계(큐브, 목표 구멍)만 넣었고, 보스의 이동 수 문구는 보스 작업 때 채운다. 곁가지: 모바일 하단 버튼이 3칸이 되며 글자가 꺾여 줄바꿈을 막았다. 캡처가 늘어 데스크톱 캡처 테스트 제한 시간을 90초로 늘렸고, 모바일 캡처는 터치 기기로 흉내 내 모바일 문구를 확인한다.

**스테이지 1.** 규칙 확인용 임시 맵을 기본 이동을 익히는 첫 스테이지 "첫걸음"으로 바꿨다. 4×3 맵에서 목표 구멍이 시작 칸 바로 옆에 보이지만 사이가 비어 있어 `↑ ↑ → → → ↓ ↓ ←`로 한 바퀴 돌아가야 하고, 최소 이동 수 8은 풀이 검사기로 구했다. 높이 차이와 오브젝트 없이 화면 하나에 들어와 `zones`는 두지 않았다. 초안은 U자 길(3방향, 8번), 한 바퀴 돌아가는 길(4방향, 8번), 좁은 통로로 잇는 두 광장(3방향, 10번) 세 개를 캡처해 비교했고, 방향키 네 개를 모두 써야 풀리는 것이 돌아가는 길뿐이라 골랐다. 갈림길과 막다른 길이 없고, 시작 칸에서는 `↑`만 움직여 다른 키를 누르면 막힘 연출로 길이 어느 쪽인지 알려준다. 가이드는 시작 칸과 목표 구멍 2단계다. 캡처 스크립트의 풀이를 새 맵으로 바꾸면서 사다리, 스위치, 상자 오르기, 메우기, 사다리 놓기, 두 번째 구역 카메라 장면은 새 맵에 없어서 뺐고 스테이지 3, 6, 9와 구역이 있는 스테이지를 만들 때 다시 넣는다. 곁가지: 구르기 중간 캡처는 새 시작 칸에서 `→`가 막혀서 `↑`로 찍는다. ARCHITECTURE의 임시 맵 탐색 시간 문장은 넓은 맵에서 다시 잰다는 뜻만 남겼다.

**다국어 구조와 영어.** 화면 문구를 모두 사전으로 옮기고 한국어와 영어를 채웠다. 라이브러리 없이 `i18n/` 폴더에 언어별 사전 파일을 두고, `en.ts`가 키의 기준이며 다른 언어는 `Partial`이라 빠진 번역은 영어로 보여준다. 새 월드를 번역보다 먼저 낼 수 있게 하기 위함이다. 문구는 `text(language, key, n?)` 순수 함수로 읽고, 화면에서는 스토어의 언어를 읽는 `useText`로 `t('clear.retry')`처럼 쓴다. `{n}`은 보스 힌트처럼 숫자가 들어가는 자리이고 항상 2 이상이라 영어 단수 복수는 나누지 않았다. 가이드 문구는 `guide.move.touch`처럼 터치 변형을 두고 변형이 없으면 기본 문구를 쓴다. 스테이지 이름과 월드 이름도 사전으로 옮겨 `stage.1-1`, `world.1`로 두고 스테이지 JSON에서 `name`을 뺐다. 언어가 늘어날 때 JSON을 건드리지 않기 위함이다. `Stage.name`은 나중에 유저가 만든 맵이 자기 이름을 넣도록 선택 필드로 남겼고 형식 `version`은 배포한 데이터가 없어 1로 뒀다. 처음 언어는 기기 언어를 따르고(한국어면 `ko`, 그 밖에는 `en`) 타이틀 구석의 목록으로 바꾸며, 고른 언어는 진행 기록과 다른 `cubound:language` 키에 저장하고 `<html lang>`도 함께 바꾼다. 언어 상태는 게임 상태와 섞이지 않게 새 `store/settingsStore.ts`에 뒀다. 언어 목록은 바깥 클릭과 Esc로 닫는다. 영어 동사는 큐브가 굴러가는 게임이라 `roll`로 통일했다. `STAGE`, `MOVES` 같은 영어 대문자 라벨은 디자인 요소라 사전에 두지 않았다. 검사는 문구 함수, 빠진 번역과 없는 언어의 영어 대체, 모든 언어에 모든 키, 모든 스테이지 이름과 가이드 문구가 사전에 있는지, 기기 언어 판단이다. Playwright는 브라우저 기본 언어가 영어라 설정에서 `ko-KR`로 고정해 기존 캡처를 지키고, 영어 캡처는 `en-US`로 따로 찍어 처음 켰을 때 영어로 시작하는 것까지 확인한다. 곁가지: 모바일 클리어 카드의 "스테이지 선택"이 두 줄로 꺾여서, 버튼 안쪽 폭 93px에 문구 폭 113px임을 재고 "스테이지"(72px)로 줄였다. 버튼 여백을 줄이는 방법은 390px에서만 들어맞고 360px에서 다시 꺾여서 기각했다. 검수에서 `Stars`의 `aria-label`이 한국어로 남은 것이 걸려서 `stars.label` 문구로 옮겼고, 쓰는 곳이 클리어 카드와 스테이지 카드 두 곳이라 props를 늘리지 않고 컴포넌트 안에서 사전을 읽게 했다. `validate.ts`의 오류 메시지는 화면에 보이지 않아 한국어로 뒀다.

**보스 이동 제한.** 스테이지 JSON에 `rules.moveLimit`을 넣으면 그 횟수 안에 도착해야 하는 보스 스테이지가 된다. 막는 곳은 `game/rules.ts`의 `move`다. 남은 이동이 0이면 움직이지 않고 지금 쓰던 막힘 이벤트를 돌려줘서 큐브가 살짝 기울었다 돌아온다. 아무 반응이 없으면 키가 안 먹은 줄 알 수 있어서 이 편을 골랐다. 순수 함수에 두면 나중에 서버가 기록을 검증할 때도 같은 결과가 나온다. `GameState`에 새 필드는 없고 `state.moves`와 스테이지의 제한만 본다. `moves`는 탐색 키에 들어가지 않아 풀이 검사기 비용은 그대로다. `solve`는 제한을 뺀 스테이지로 탐색한다. 제한을 모른 채 맵을 먼저 만들다 제한을 너무 작게 적으면 "못 푸는 맵"과 구분이 안 되기 때문이고, 이제 `validateStage`가 "moveLimit이 best보다 작다"로 짚어준다. 검사는 양의 정수와 `best` 이상이고, 선택 필드라 형식 `version`은 1로 뒀다. 별 기준도 맞췄다. `stars(moves, best, limit)`의 세 번째 값이 ★★ 경계이고, 제한이 있는 스테이지는 그 제한을, 없으면 지금처럼 `moveLimit(best)`(최소 + 20% 올림)를 쓴다. 두 값이 다르면 "제한 안에 들어왔는데 ★ 하나"가 나오기 때문이다. 제한을 넘겨서는 클리어할 수 없어 보스에서 ★ 하나는 나오지 않는다. 화면은 제한이 있는 스테이지에서만 `MOVES` 자리를 `LEFT`와 남은 수로 바꾸고, 0이 되면 재시작 버튼을 진한 면(`bg-ink`)으로 바꿔 강조한다. 호버 색 규칙 표의 "진한 면"과 같은 표현이라 새 시각 언어를 만들지 않고 움직임도 없다. `Button`에 `strong` 옵션을 넣으면서 배경과 호버 색이 한 문자열에 섞여 있던 `secondary`와 `icon`을 색만 `TONES`로 떼어냈다. 스테이지 선택의 보스 카드 제한은 `moveLimit(stage.best)` 계산값 대신 JSON의 `rules.moveLimit`을 보여준다. 가이드 문구 `guide.moveLimit`을 한국어와 영어로 넣었고, `{n}` 치환이 `text`에만 있고 `guideText`에는 없어서 두 함수가 함께 쓰는 `fill`로 뺐다. 영어는 카드의 `Arrive in {n} moves`와 겹치지 않게 `You have {n} moves to get home`으로 했다. 확인은 `01.json`에 제한 10과 보스 가이드 단계를 임시로 넣고 임시 스크립트로 데스크톱과 모바일, 한국어와 영어를 찍은 뒤 되돌렸다. 영어 `Arrive in 24 moves`는 390px 보스 카드에서 한 줄에 들어가 줄이지 않았다. 스테이지 10 맵은 아직 없다. 곁가지: 가이드 카드가 숫자를 받아야 해서 `GuideOverlay`에 `moveLimit` props를 더했다. 스테이지 선택 화면의 보스 힌트는 전부터 모바일에서만 보이고 데스크톱에서는 숨어 있어 그대로 두었다.

**모바일 스와이프.** 필드를 스와이프한 대각선 방향으로 큐브가 한 칸 움직인다. 방향은 `platform/input.ts`의 `directionFromSwipe`가 화면 좌표 변화량의 부호만 보고 정한다. 아이소메트릭 네 축이 화면 가로축과 세로축 기준으로 대칭이라 가장 가까운 축을 골라도 경계가 가로선과 세로선이 되고, 칸 가로세로 비율을 보정할 필요가 없었다. 최소 거리는 28px로 뒀다. 탭할 때 손가락 흔들림이 보통 10px 미만이라 톡 치는 동작과 구분되고 390px 폭의 7% 정도다. 최소 거리를 넘는 순간 바로 판정하고 시작점을 비워 한 제스처에 한 칸만 움직인다. 별점이 이동 수 기준이고 되돌리기가 없어 의도보다 한 칸 더 가면 손해가 크기 때문이다. 손을 떼지 않고 계속 밀 때 거리마다 한 칸씩 더 나가는 방식은 실수로 지나칠 위험이 있어 빼고, 여덟 번 떼는 게 답답한지 사용자에게 묻기로 했다. 수평이나 수직에 가까운 애매한 각도도 무시하지 않고 부호대로 정한다. 무시하면 아무 반응이 없어 고장난 것처럼 느껴지고, 이 게임엔 가로 이동이 없어 완전히 수평인 스와이프는 의도된 입력이 아니다. 키보드와 같은 스토어의 `move`로 들어가서 입력 대기열, 연달아 이동, 가이드 중 막기가 그대로 적용되고 `gameStore.ts`는 고치지 않았다. 마우스 드래그도 같은 Pointer 이벤트로 받아 터치와 구분하지 않는다. 사용자가 Windows PC 웹으로만 확인해서 터치만 받으면 폰 없이는 만져 볼 수 없기 때문이다. 필드 영역에 `touch-none`과 `select-none`을 둬서 스와이프 중 화면이 끌리거나 당겨서 새로고침되지 않고 드래그로 글자가 선택되지 않는다. 가이드 중에는 오버레이가 화면 전체를 덮어 스와이프가 필드에 닿지 않고 탭 넘기기는 그대로다. 검증은 단위 테스트 8개(네 방향, 최소 거리 미만, 경계, 수평과 수직에 가까운 각도)와 스모크 1개다. Playwright에 터치 드래그가 없어 CDP `Input.dispatchTouchEvent`로 터치를 직접 보내 가이드 중에는 이동이 0이고 탭으로 넘긴 뒤에는 움직이는 것을 확인한다. 화면 모양은 바뀌지 않아 캡처는 그대로 두었다.

**스테이지 2.** 높이를 가르치는 두 번째 스테이지 "내리막 / Downhill"을 만들었다. 6×6 맵에서 큐브는 높이 2인 능선 위에서 시작하고, 집은 반대쪽 끝 바닥에 있다. 최소 이동 수 13은 풀이 검사기로 구했다. 못 올라간다는 것을 두 번 겪는다. 능선에서 내려선 평지에서 집 쪽으로 가려 하면 둔덕에 막히고, 아래 골에서 집 쪽으로 내려가려 해도 둔덕에 막혀 왼쪽 끝까지 되돌아와야 한다. 오른쪽 끝 열은 위아래로 이어진 높이 2 능선인데 여기를 끝까지 타고 가면 15번이라, 일찍 내려오는 쪽이 2번 짧다. 이것이 "내려가는 것이 지름길"이다. 이 게임은 몇 층을 떨어지든 이동 1회라 절벽이 계단보다 빠른 지름길은 규칙상 만들어지지 않고, 대신 "높은 데 머물면 돌아가게 된다"로 같은 것을 가르친다. 빈 칸(-1)은 쓰지 않았다. 스테이지 1이 빈 칸으로 길을 막았으니 2는 높이로만 막아야 대비가 선명하다. 목표를 가장 낮은 층에 두고 0층 칸을 전부 하나로 이어서, 어디로 내려가도 집까지 갈 수 있고 내려갔다 막히는 자리가 구조적으로 생기지 않는다. 시작에서 닿을 수 있는 모든 칸에서 집까지 갈 수 있는지 임시 스크립트로 전수 확인했다. 가이드는 집 앞을 막는 둔덕 칸 하나를 비추는 1단계이고 문구는 이미 있던 `guide.height`를 쓴다. 높은 면과 낮은 면이 한 화면에 보이고 시작하자마자 그 둔덕에 막히게 된다. 초안은 셋을 만들어 캡처해 비교했다. A 둔덕 하나(5×4, 11번)는 가장 짧지만 어디로 내려와도 같은 수라 내려가기가 지름길이 되지 않았고, C 세 갈래 골(6×6, 15번)은 최단 경로에 들어가지 않는 함정 통로가 있어 헛걸음이 최대 10번으로 스테이지 2치고 벌이 셌다. B는 요청한 세 조건을 모두 만족하고 못 올라감을 두 번 겪어서 골랐다. 방향키는 ↑를 쓰지 않는데, 길을 막는 수단이 높은 칸뿐이라 위에서 아래로 내려오는 맵은 자연히 세 방향만 쓰게 된다. 네 방향은 상자가 나오는 3~5부터 고루 쓰기로 했다. `zones`와 `rules.moveLimit`은 두지 않았다. 캡처 스크립트에 스테이지 2 장면을 더했다. 데스크톱은 스테이지 1 클리어 카드에 처음 생긴 "다음 스테이지" 버튼으로 넘어가고, 모바일은 스테이지 선택에서 해금된 02를 눌러 들어간다. 앞쪽 둔덕이 큐브를 가리는 자리도 함께 찍어 가림 처리가 도는 것을 확인했다. 곁가지: ARCHITECTURE "배포"에 실제 주소와 자동 배포를 적었다.

**스테이지 3~5.** 상자를 가르치는 세 스테이지를 만들었다. 3 "디딤돌 / Stepping Stone"은 상자를 계단으로, 4 "건널목 / The Crossing"은 다리로, 5 "골짜기 / The Valley"는 둘을 섞는다. 셋 다 최소 이동 수 14이고 풀이 검사기로 구했다. 길이 대신 다루는 개념 수로 난이도를 올렸다. 구역을 처음 썼다. 3은 구덩이와 골목, 4는 마당과 들판, 5는 구덩이와 골짜기로 나눴고 모두 두 개다. 이어지는 칸을 두 구역이 함께 덮게 두어 넘나드는 순간에 카메라가 한 번만 움직인다. 상자가 있는 맵의 어려움은 되돌릴 수 없는 실수였다. 이 규칙에서는 상자를 당길 수 없어서 한 줄 끝까지 밀린 상자는 영영 못 움직인다. 반대로 상자 뒤가 한 층 높거나 맵 밖이면 밀기가 실패하고 큐브가 상자 위로 올라갈 뿐이라 아무 손해가 없다. 그래서 가르치려는 방향만 열어 두고 나머지를 높은 칸으로 막는 방식으로 설계했다. 확인은 시작에서 닿는 모든 상태를 펼친 뒤 목표에서 역방향으로 훑어 "여기서 목표까지 갈 수 없는 상태" 수와 가장 빨리 빠지는 이동 수를 세는 임시 스크립트로 했다. 3은 막히는 상태가 0개이고, 4는 7수, 5는 9수부터 생긴다. 3은 배우는 단계라 0개로 맞췄고 4와 5는 실수를 허용하되 저지른 자리와 알아채는 자리를 가깝게 뒀다. 3은 초안 셋을 캡처해 비교했다. A 구덩이 하나에 상자 하나(13번)는 두 번째 구역이 걷기만 하는 빈 구간이었고, C 긴 골목(13번)은 오른쪽 키만 열세 번 눌러 스테이지 1이 가르친 네 방향이 무색해졌다. B는 구덩이(상자를 아무 벽으로나 밀어도 나올 수 있어 막히지 않음)와 폭 1칸 골목(상자가 앞으로만 밀림)으로 같은 배움을 두 가지 형태로 겪게 해서 골랐다. 4는 초안 둘을 비교했다. 4-2 두 조각 다리(협곡 두 칸을 상자 두 개로 메우기, 15번)는 "상자 하나가 한 칸을 메운다"가 또렷하지만 지형이 폭 1~3칸 띠라 화면이 밋밋했고, 시작에서 왼쪽 두 번이면 2수 만에 막혔다. 4-1은 첫 협곡의 상자가 협곡 쪽으로만 밀려 막히지 않고, 둘째 협곡은 건너편에 바닥이 있는 줄이 하나뿐이라 "밀기 전에 건너편을 본다"가 유일한 막힘 이유가 된다. 최적 풀이가 9수에서 상자 위에 올라섰다 반대편으로 내려서는 길을 써서 3에서 배운 계단이 자연스럽게 섞인다. 5는 초안 둘을 비교했고, 5-2 건너고 오르기(15번)는 4-2와 구조가 같아 4와 5가 같은 스테이지처럼 느껴져 뺐다. 5-1은 상자 셋을 계단, 다리, 계단으로 다르게 쓰는데 가운데 다리를 큐브가 높이 1에서 밀어 메운 칸도 높이 1이 된다. "밀던 높이의 바닥이 된다"는 규칙이 처음 눈에 보이는 자리다. 이름은 짧은 명사로 앞 스테이지와 결을 맞췄다. "첫 상자"는 "첫걸음"과 앞글자가 겹치고 "다리 놓기"는 설명문 같고 "세 상자"는 내용을 미리 알려줘서 뺐다. 탐색 시간은 3이 14ms, 4가 6ms, 5가 30ms로 상자가 셋이어도 넉넉했다. 캡처 스크립트에 세 스테이지를 더했다. 스테이지마다 찍을 이동 번호를 표로 두고 한 함수가 풀이를 두면서 그 장면과 클리어 카드를 찍는다. 상자를 밀고 올라서는 장면, 구역이 바뀐 뒤, 다리를 놓은 직후와 그 위에 선 모습, 높은 다리, 앞쪽 높은 칸이 큐브를 가리는 자리를 데스크톱과 모바일에서 찍는다. 장면이 늘어 두 캡처 테스트의 제한 시간을 300초로 올렸다. 곁가지: 클리어 카드의 "스테이지" 버튼이 같은 카드의 "다음 스테이지"와 헷갈려 `clear.select`를 "목록 / All stages"로 바꿨다. 게임 화면 툴팁 `play.select`("스테이지 선택")는 그대로다.

**화면 다듬기.** 구역이 둘인 스테이지에서 첫 화면이 아래와 오른쪽으로 치우쳐 보이고, 화면이 작을수록 필드가 작아 보이는 문제를 고쳤다. 짐작하지 않고 Playwright로 세 화면 크기(1920×1080, 1440×800, 390×844)에서 스테이지 3~5의 여백을 먼저 쟀다. 원인은 둘이었다. 첫째, `viewBoxFor`가 칸 위에 선 큐브 몫으로 `TILE.layer * 2`(60)를 위쪽에만 더해서 지형이 그만큼 아래로 내려갔다. 측정치도 정확히 그랬다(1920에서 위 185px 아래 74px, 차이 111px = 60 × 배율 1.855). 이 60은 실제 필요량의 2.5배였다. 큐브가 칸 윗면보다 솟는 양은 제자리 19, 45도로 구르는 중 24, 든 사다리 24다. 둘째, `Board`가 구역과 상관없이 모든 칸을 그리는데 SVG는 viewBox가 아니라 요소 박스에서 잘라서, 비율이 남는 자리에 구역 밖 지형이 또렷하게 나왔다. 구역 자체는 좌우 여백이 언제나 같았고(372/372) 가로 치우침은 전부 구역 밖 지형이 만든 것이었다. 스테이지 4가 가장 심해 왼쪽 여백 470px인데 오른쪽으로 149px 넘쳐 잘렸다. 작은 화면의 큰 여백은 `MARGIN`(40 유닛) 탓이 아니라 구역 비율과 화면 비율 차이였다. 폰의 필드 영역은 324×612인데 구역은 572×332 유닛이라 위아래로 223px씩 letterbox가 남고, 배율이 가로에 묶여서 위아래 여백을 줄여도 칸이 커지지 않는다. 고친 방식은 계산을 `zoneBox`(구역이 그려지는 범위, 칸 높이와 바닥 두께 포함, 위아래에 한 층씩 같은 여유)와 `viewBoxFor`(그 범위를 필드 한가운데에 놓고 화면과 같은 비율의 viewBox를 만듦, 여백은 한 변의 4%)두 순수 함수로 나눈 것이다. 화면 비율을 맞춰 letterbox를 없앴기 때문에 `useCamera`가 필드 크기를 알아야 해서 `ResizeObserver`로 잰다. 보간은 viewBox가 아니라 구역 범위에 걸어서, 구역이 바뀔 때만 0.6초 동안 움직이고 창 크기 변화는 바로 반영된다. 결과는 구역 여백이 상하좌우 완전히 대칭이 되고(1920 상97 하97 좌315 우315) 배율이 스테이지 3에서 1.855 → 2.055, 스테이지 4에서 2.379 → 2.797로 올랐다. 화면에서 구역이 차지하는 면적은 1920에서 41% → 51%, 1440에서 38% → 47%, 390에서 24% → 27%다. 폰은 `PlayScreen`의 필드 여백을 모바일에서만 `p-4` → `p-2`로 줄여 가로 324 → 340px을 얻어 배율이 0.497 → 0.547(+10%)이 됐고, 그 이상은 구역 안에서 큐브를 따라가지 않는 한 방법이 없어 나중 작업으로 남겼다. 구역 밖 지형은 또렷하게 그린다. 한 구역이 한 퍼즐로 읽히게 투명도 0.5로 옅게 그려 봤는데, 직접 해보니 상자 위에 올라서서 다음에 갈 곳을 볼 때 흐릿해 더 헷갈려서 되돌렸다. 가운데 정렬로 쏠림이 이미 해결되어 옅게 할 이유도 없었다. 여기까지 하고 나니 스테이지 4 첫 화면만 너무 가깝게 확대돼 보여서 확대 상한을 뒀다. 구역이 작으면 화면을 채우려다 칸이 커지는 게 원인이다. 1440×800에서 칸 폭을 재보니 스테이지 4 첫 구역이 198px, 스테이지 1이 221px인데 나머지는 127~145px이었다(구역 범위가 스테이지 4 첫 구역은 364×288, 스테이지 3 첫 구역은 572×392이라 작은 구역이 더 확대된다). 그래서 칸 폭 상한을 145px로 두고 배율을 고르는 `Math.min`에 항목으로 넣었다. 확대만 막아서 구역이 화면보다 커 배율이 이미 작을 때는 걸리지 않고, 폰(칸 폭 52~89px)에서는 아예 걸리지 않아 앞서 키운 폰 화면이 그대로다. 상한 145, 160, 175를 스테이지 4와 스테이지 1에서 1440과 1920으로 캡처해 비교했다. 175는 둘째 구역의 상자가 화면 밖으로 잘리고, 145에서 스테이지 4 첫 구역이 스테이지 3, 5의 첫 구역과 같은 145px이 됐다. 구역 사이 배율 차이도 줄었다. 1440에서 스테이지 4는 198 → 136(1.46배)이었는데 145 → 136(1.07배)이 되어 전환이 거의 이동만 남는다. 1920에서는 291 → 200(1.46배)이 145 → 145(1.0배)다. 대신 구역이 없는 스테이지 1, 2는 주변 지형이 없어서 남는 자리가 빈 배경이 된다. 1440에서 스테이지 1은 221 → 145로 작아졌고 1920에서는 325 → 145로 더 작아진다. 가림 처리 투명도는 0.35에서 0.5로 올렸다. 큐브가 앞 칸에 가장 많이 가려지는 두 자리(스테이지 2의 8수, 스테이지 3의 8수)를 세 값으로 확대 캡처해 비교했는데, 0.35는 앞 칸이 거의 사라져 벽에 구멍이 난 것처럼 보이고 0.65는 칸이 또렷히 남는 대신 큐브 오른쪽 면이 눈에 띄게 흐려졌다. 여백 비율 4%도 같은 방식으로 후보를 캡처해 비교하고 정했다. 검증은 카메라 계산 테스트 11개를 먼저 쓰고 구현했다. 구역이 한가운데 오는가, 화면 비율이 달라도 다 들어오는가, viewBox 비율이 화면과 같은가, 화면이 커져도 차지하는 비율이 같은가, 그리고 `rollingCubeFaces`로 구르는 도중까지 계산해 가장 높은 칸 위의 큐브가 잘리지 않는가를 검사한다. 가장 높고 뒤쪽인 칸에서 구르는 중간 프레임도 데스크톱과 폰으로 찍어 확인했다. 연출은 느려지지 않았다. CPU 4배 느림 조건에서 같은 상자 밀기를 세 번씩 재서 고치기 전 평균 20.2~22.0ms(끊김 7~8프레임), 고친 뒤 16.7~21.5ms(끊김 0~8프레임)로 이전 기록 17.5ms와 같은 수준이다. 곁가지: `game/camera.ts`의 private `contains`를 `inZone`으로 이름을 바꿔 내보내 카메라 범위 계산이 구역 안 판정에 같은 함수를 쓴다.
