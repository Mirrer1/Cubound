# 공통 규칙

> 모든 작업에 적용. 파일 종류별 규칙은 같은 폴더의 다른 파일이 해당 파일을 다룰 때 자동 적용된다.

## 버전 주의

- Vite 8, React 19, TypeScript 6, Tailwind CSS v4, Vitest 4, Motion은 학습 데이터와 API가 다를 수 있다. 확신이 없으면 `node_modules`의 타입 정의나 문서를 확인한다
- Tailwind v4는 `tailwind.config.js`가 없다. 설정과 색 토큰은 `apps/web/src/index.css`의 `@theme`에서 한다
- Node.js 22.12 이상이 필요하다. 낮으면 Vite와 oxlint의 네이티브 모듈이 설치되지 않는다

## 협업 방식

1. 코드 변경 전 설명하고 승인받는다. 임의로 결정하지 않는다
2. 단계별로 진행한다. 한 번에 여러 기능을 섞지 않는다
3. 짧고 핵심만 설명한다
4. 외부 계정 가입, 배포, 환경 변수 등록은 사용자가 직접 한다. 명령어와 순서만 안내한다
5. 막히면 질문부터 한다

## 작업 흐름 (커밋 1단위)

1. 기능 구현
2. `pnpm build`, `pnpm lint`, `pnpm test`로 확인. 화면을 바꿨으면 `pnpm shot`으로 캡처해 직접 본다
3. 사용자가 로컬에서 확인할 것이 있으면 실행 명령어와 확인 항목을 안내한다
4. 사용자가 결과를 알려준다
5. 문제가 있으면 수정하고, 없으면 커밋명을 추천한다
6. `/update-docs`로 문서를 갱신한다

## 주석 스타일

**주석은 최소화한다.** 이름과 코드로 드러나는 내용에는 달지 않고, 드러나지 않는 의미나 이유가 있을 때만 짧게 단다.

| 위치                            | 주석                                                        |
| ------------------------------- | ----------------------------------------------------------- |
| 인터페이스와 타입 필드          | 값의 의미가 이름만으로 불분명할 때 필드 뒤 `// 짧게`        |
| 컴포넌트, 함수, 콜백, useEffect | 이름만으로 동작이나 이유가 드러나지 않을 때 위에 `// 한 줄` |
| state, 일반 변수, JSX           | 달지 않음                                                   |

- 한 문장으로 사실 위주로 담백하게 쓴다. 수식어와 비유는 쓰지 않는다
- 두 절을 콤마로 잇지 않는다. `~고`, `~며`, `~서`로 한 문장으로 묶거나 핵심만 남긴다
- 한글 단어를 나열할 때 `·`, `/`, `+`를 쓰지 않는다. 포괄 단어 하나로 묶고, 없으면 `~와`/`~과`, 그래도 없으면 콤마
- `~지 않음` 같은 부정형 대신 긍정 명사형으로 쓴다 (예: "이동하지 않음" → "제자리 유지")
- 영어 코드 식별자와 약어는 그대로 둔다
- 괄호 부연설명, 특수문자 장식(`── ──`, `=`), 다른 코드와의 관계나 비교 언급, JSDoc(`/** */`)은 쓰지 않는다

## 파일, 폴더 명명

- 컴포넌트 `PascalCase.tsx`, 훅 `useXxx.ts`, 유틸과 타입과 로직 `camelCase.ts`
- 스테이지 데이터는 `world-1/01.json`처럼 월드 폴더와 두 자리 번호
- 폴더는 한 단어면 소문자, 합성 단어면 `camelCase`
- 기능에 종속된 컴포넌트는 스코프 접두어를 붙인다 (필드 `BoardCell`, 스테이지 선택 `StageCard`). 공용 컴포넌트는 접두어 없음

## 위치

- 앱과 패키지 구분, 의존성 위치, catalog, tsconfig 확장 규칙은 `CLAUDE.md` "프로젝트 구조"를 따른다
- `apps/web/src/` 안의 폴더 역할은 `docs/ARCHITECTURE.md` "web 폴더 구조"를 따른다
- 게임 규칙은 `game/`, 브라우저와 앱 환경에 의존하는 코드(저장, 입력)는 `platform/`에만 둔다
- import는 `@/` 경로 별칭을 쓴다. 같은 폴더 안은 `./`를 허용한다
- 공유 타입은 `game/types.ts`, Props와 작은 로컬 타입은 그 파일 안. 2~3곳 이상 반복되면 공유 타입으로 올린다

## 상수

- 한 파일 안에서 3곳 이상 쓰면 파일 상단 대문자 상수로 분리하고, 1~2곳이면 인라인
- 색은 상수가 아니라 `index.css`의 `@theme` 토큰으로 둔다
- 별도 `constants/` 폴더는 만들지 않는다

## 화면 문구

- 화면에 보이는 문구는 코드에 직접 쓰지 않고 `apps/web/src/i18n/`의 사전에 둔다. **새 문구는 지원하는 여섯 언어에 모두 넣는다.** 스테이지와 월드 이름도 마찬가지다
- **월드를 만들기 전에 그 열 판의 이름을 여섯 언어로 먼저 채운다.** 한두 언어만 채우면 나머지 언어 화면에 영어가 섞여 나온다. `i18n.test.ts`가 빠진 것을 잡는다
- `STAGE`, `MOVES` 같은 영어 대문자 라벨은 디자인 요소라 사전에 두지 않는다
- 구조와 빠진 번역 처리는 `docs/ARCHITECTURE.md` "문구와 다국어"를 따른다

## 포맷

- Prettier가 기준이다 (`.prettierrc`). 세미콜론 없음, 작은따옴표, 100자
- import는 외부 라이브러리, 내부 파일, CSS 순서로 그룹 사이에 빈 줄을 둔다. 정렬은 Prettier 플러그인이 한다
- Tailwind 클래스 순서는 Prettier 플러그인이 정렬한다
- 작업을 마치면 `pnpm format`을 실행한다
- 커밋 전 Husky가 lint-staged로 staged 파일에 oxlint와 Prettier를 돌린다. 설정은 루트 `package.json`의 `lint-staged`
- 줄바꿈은 LF로 고정한다 (`.gitattributes`)

## 커밋과 Git

- 브랜치는 `main` 하나, 이슈와 PR 없음
- 커밋 메시지는 prefix(`feat:`, `fix:`, `refactor:`, `chore:`, `test:`, `style:`, `docs:`) + 한 개념으로 뭉뚱그린 한 구절
- 여러 변경은 나열하지 말고 상위 개념 하나로 일반화한다
- `및`, `/`, `~와`, `~과` 같은 연결자와 `변경`, `수정` 같은 군더더기, `을`/`를` 조사는 뺀다
- 예: `feat: 상자 밀기 규칙`, `fix: 높은 칸 상자 낙하 위치`
- 커밋은 사용자가 직접 한다. Claude는 커밋명만 추천한다
