# 문서 갱신

## 1. 무엇이 바뀌었나 파악

- git 저장소라면 `git log --oneline`에서 마지막 `docs:` 커밋 이후 커밋들과 `git diff`로 이번 작업 범위를 확인한다
- 대화에서 정한 결정(왜 이렇게 했는지, 무엇을 검토하고 버렸는지)이 있으면 함께 반영한다

## 2. 문서별로 넣을 곳

| 바뀐 것                                  | 갱신할 곳                                                  |
| ---------------------------------------- | ---------------------------------------------------------- |
| 기능 구현 (항상)                         | `.claude/history.md` 맨 끝에 항목 추가                     |
| 진행 상황, 명령어, 기술 스택 변경        | `CLAUDE.md`의 "현재 상태", "자주 쓰는 명령어", "기술 스택" |
| 게임 규칙, 오브젝트, 스테이지 구성, 범위 | `docs/PRD.md`                                              |
| 구조, 게임 모델, 렌더링, 저장, 배포 결정 | `docs/ARCHITECTURE.md`                                     |
| 화면, 색, 오브젝트 형태, 모션 방향       | `docs/DESIGN_BRIEF.md`                                     |
| 코딩 규칙이 새로 생기거나 바뀜           | `.claude/rules/code/`의 해당 파일                          |
| 새 영역이 생겨 기존 rules에 안 맞음      | `.claude/rules/code/`에 새 파일 + `paths` 지정             |
| 밖에서 보이는 것이 바뀜                  | `README.md` (아래 "README 확인")                           |

## README 확인

`README.md`는 저장소를 처음 여는 사람이 읽는 유일한 문서라 다른 문서를 고칠 때 함께 본다. 아래가 바뀌면 README도 고친다.

| 바뀐 것                      | README에서 고칠 곳    |
| ---------------------------- | --------------------- |
| 새 오브젝트, 오브젝트 규칙   | "오브젝트" 표         |
| 화면이나 기능이 늘고 바뀜    | "주요 기능"           |
| 주소 추가                    | "라우트" 표           |
| 라이브러리나 저장 키 변경    | "기술 스택" 표        |
| `package.json` 스크립트 변경 | "스크립트" 표         |
| 폴더가 생기거나 역할이 바뀜  | "프로젝트 구조"       |
| 구조 결정을 뒤집음           | "설계 노트"           |
| 월드 진행, 배포 상태         | "오브젝트" 절 끝 문단 |

- README는 홍보 문서가 아니라 **사실 문서**다. 아직 안 만든 것을 만든 것처럼 쓰지 않는다. 계획은 "(예정)"으로 표시한다
- 설계 노트에 숫자를 적었다면 그 숫자가 아직 맞는지 확인한다
- 다른 문서와 같은 내용을 길게 옮겨 적지 않는다. 자세한 것은 `docs/PRD.md`처럼 파일명으로 가리킨다

원칙:

- `CLAUDE.md`와 `paths` 없는 rules는 매 대화 읽히므로 짧게 유지한다
- 문서엔 "무엇을, 왜"만 쓰고 코드로 확인되는 세부(타입 필드, 스테이지 좌표)는 쓰지 않는다. 기준 파일(`game/types.ts`)을 가리킨다
- 같은 내용을 여러 파일에 쓰지 않는다. 한 파일에 두고 다른 파일에선 파일명으로 가리킨다
- 기존 결정을 뒤집었으면 옛 문장을 지우고 새 결정과 이유로 교체한다. 버린 대안이 의미 있으면 "기각한 대안"으로 한 줄 남긴다
- `paths` glob이 실제 파일과 맞는지 확인한다
- 코드 이름(함수, 파일, 숫자 값)을 적었다면 실제 코드에 있는지 grep으로 확인한다

## 3. history.md 항목 형식

- `**굵은 제목.**`으로 시작하는 한 문단 (한 작업 묶음 = 한 항목, 최신이 맨 뒤)
- 무엇을 했나 → 어떻게(핵심 파일과 함수는 백틱) → 왜 그렇게 했나 순서
- 사용자 입장의 동작 설명을 먼저 쓴다
- 부수 작업은 문단 끝에 `곁가지:`로 붙인다

예:

```md
**상자 밀기.** 큐브가 상자 쪽으로 이동하면 상자가 한 칸 밀리고, 낮은 칸이면 떨어지고 빈 칸이면 메워진다. `game/rules.ts`의 `pushBox`가 처리하고 결과를 `pushed` 이벤트로 돌려준다. 풀이 검사기가 같은 함수를 써야 해서 화면 쪽에 규칙을 두지 않았다. 곁가지: 3스테이지 JSON 추가.
```

## 4. 마무리

- `pnpm format`으로 수정한 md 파일을 정리한다
- 커밋은 사용자가 직접 한다. 커밋명은 `docs: 문서 갱신` 형태로 추천한다
