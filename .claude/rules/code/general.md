# 공통 규칙

> 모든 작업에 적용. 파일 종류별 규칙은 같은 폴더의 다른 파일이 해당 파일을 다룰 때 자동 적용된다.

## 버전 주의

- Vite 8, React 19, TypeScript 6, Tailwind CSS v4, Vitest 4, Motion은 학습 데이터와 API가 다를 수 있다. 확신이 없으면 `node_modules`의 타입 정의나 문서를 확인한다
- Tailwind v4는 `tailwind.config.js`가 없다. 설정과 색 토큰은 `apps/web/src/index.css`의 `@theme`에서 한다
- Node.js 22.12 이상이 필요하다. 낮으면 Vite와 oxlint의 네이티브 모듈이 설치되지 않는다

## 협업 방식

1. 코드 변경 전 설명하고 승인받는다. 임의로 결정하지 않는다
2. 단계별로 진행한다. 한 번에 여러 기능을 섞지 않는다
3. 짧고 핵심만 설명한다
4. 외부 계정 가입, 배포, 환경 변수 등록은 사용자가 직접 한다. 명령어와 순서만 안내한다
5. 막히면 질문부터 한다

## 작업 흐름 (커밋 1단위)

1. 기능 구현
2. `pnpm build`, `pnpm lint`, `pnpm test`로 확인. 화면을 바꿨으면 `pnpm shot`으로 캡처해 직접 본다. diff에 새로 생긴 주석은 아래 "주석 스타일"에 맞는지 하나씩 본다
3. 사용자가 로컬에서 확인할 것이 있으면 실행 명령어와 확인 항목을 안내한다
4. 사용자가 결과를 알려준다
5. 문제가 있으면 수정하고, 없으면 커밋명을 추천한다
6. `/update-docs`로 문서를 갱신한다

## 주석 스타일

**주석은 최소화한다.** 이름과 코드로 드러나는 내용에는 달지 않고, 드러나지 않는 의미나 이유가 있을 때만 짧게 단다. 남길 것은 왜 이 순서인지, 숫자가 무엇을 뜻하는지, 일부러 이렇게 둔 함정 같은 것이다. 과하거나 덜어낼 수 있는 주석은 지운다.

| 위치                            | 주석                                                        |
| ------------------------------- | ----------------------------------------------------------- |
| 인터페이스와 타입 필드          | 값의 의미가 이름만으로 불분명할 때 필드 뒤 `// 짧게`        |
| 컴포넌트, 함수, 콜백, useEffect | 이름만으로 동작이나 이유가 드러나지 않을 때 위에 `// 한 줄` |
| state, 일반 변수, JSX           | 달지 않음                                                   |

- 한 줄에 명사로 끝나는 한 구절로 사실 위주로 담백하게 쓴다. 수식어와 비유는 쓰지 않는다 (예: "콩나무는 세 층까지 솟는다" → "콩나무 최대 높이 세 층")
- 마지막 단어로 `~다`, `~ㅁ/~음/~함`(버팀, 셈), 조사(`~때만`, `~까지`, `~에서`)를 쓰지 않는다. 뜻이 흐려지면 불가, 예외, 기준, 경우, 수, 칸, 높이 같은 명사로 맺는다
- 부정형 대신 긍정 명사를 쓴다 (예: "다시 지날 수 없다" → "통행 불가", "이동하지 않음" → "제자리 유지")
- 두 가지를 말해야 하면 명사 구절을 쉼표로 잇는다 (예: "큐브만 미는 바람, 늪에 선 큐브와 숨은 큐브는 예외"). 서술하는 두 절은 콤마로 잇지 않는다
- 두 줄은 한 줄로 뜻이 서지 않을 때만 쓰고 세 줄 이상은 쓰지 않는다
- 설명을 늘어놓는 말투, "~하기 위해서" 꼴의 군더더기, 같은 말 되풀이를 쓰지 않는다. 언제 왜 바꿨는지는 `history.md` 몫이다
- **고치는 작업에서는 주석을 새로 달지 않는 것이 기본이다.** 고친 이유와 전에 어땠는지는 커밋 메시지와 `history.md` 몫이다. 코드만으로 알 수 없는 이유가 새로 생겼을 때만 단다
- 코드를 고쳐 기존 주석이 틀려지면 같이 고치고, 쓸모가 없어지면 지운다
- 한글 단어를 나열할 때 `·`, `/`, `+`를 쓰지 않는다. 포괄 단어 하나로 묶고, 없으면 `~와`/`~과`, 그래도 없으면 콤마
- 영어 코드 식별자와 약어는 그대로 둔다
- 50판 묶음은 문서와 커밋 메시지에서 "챕터"라고 쓴다(화면은 `CHAPTER`). "사이클"은 쓰지 않는다. 코드 이름(`data-cycle`, `cycleOf`)은 그대로 둔다
- 주석과 문서(`.md`), 커밋 메시지에 이모지를 쓰지 않는다. 깃허브에 그대로 보여 AI가 쓴 티가 난다. 방향키(↑ → ↓ ←)와 별점(★)처럼 뜻이 있는 기호는 쓴다
- 괄호 부연설명, 특수문자 장식(`── ──`, `=`), 다른 코드와의 관계나 비교 언급, JSDoc(`/** */`)은 쓰지 않는다

## 파일, 폴더 명명

- 컴포넌트 `PascalCase.tsx`, 훅 `useXxx.ts`, 유틸과 타입과 로직 `camelCase.ts`
- 스테이지 데이터는 `world-1/01.json`처럼 월드 폴더와 두 자리 번호
- 폴더는 한 단어면 소문자, 합성 단어면 `camelCase`
- 기능에 종속된 컴포넌트는 스코프 접두어를 붙인다 (필드 `BoardCell`, 스테이지 선택 `StageCard`). 공용 컴포넌트는 접두어 없음

## 위치와 구조

**구조는 2챕터 뒤 한 번 크게 정리했다 (`history.md` "구조 정리").** 다시 한 파일에 쌓이지 않게 아래를 지킨다.

- 앱과 패키지 구분, 의존성 위치, catalog, tsconfig 확장 규칙은 `CLAUDE.md` "프로젝트 구조"를 따른다
- `apps/web/src/` 안의 폴더 역할은 `docs/ARCHITECTURE.md` "web 폴더 구조"를 따른다
- 게임 규칙은 `game/`, 브라우저와 앱 환경에 의존하는 코드(저장, 입력)는 `platform/`에만 둔다
- 훅은 `src/hooks/`, 주소와 탭 제목은 `src/routes/`에 둔다. `components/board/`에는 화면 컴포넌트만 두고 시간에 따라 바뀌는 연출 계산은 `frame/`, 시간과 무관한 그림 계산은 `view/`에 둔다
- **새 요소는 요소마다 파일을 더한다.** 규칙은 `game/rules/<요소>Rule.ts`, 연출 계산은 `components/board/frame/<요소>Frame.ts`, 그림은 `components/board/Board<요소>.tsx`, 형식 검사는 `game/validate/<요소>Check.ts`다. 그 순간 값은 `sceneFrame`에, 칸에 넘길 값은 `cellLookFrame`의 `CellLook`에 그 요소의 묶음 하나로 더한다. 있는 파일 끝에 덧붙이지 않는다
- **칸 위에 서는 새 요소는 가이드 사각형(`frame/guideFrame.ts`의 `guideRect`)도 같이 맞춘다.** 사각형은 요소를 모르면 칸 윗면 높이로만 재서 요소가 위로 삐져나오거나 치우친다. 얼음 돌이 그랬다(121). 높이를 `reachOf`에 더하고, 가이드 화면을 3배 확대 캡처해 요소가 사각형 가운데에 오는지 본다. 다른 요소의 사각형은 사용자가 한 번에 다 검토해 맞춘 것이라 건드리지 않는다
- **보스 가이드도 같다.** 칸을 비추는 보스(70, 80, 110, 120)는 위 줄대로 보고, 화면 숫자를 비추는 보스(10 `MOVES`, 100 바람 같은)는 숫자 요소에 `data-guide="<이름>"`을 붙이고 그 이름을 `game/types.ts`의 `GuideTarget`과 `game/validate/guideCheck.ts`의 `GUIDE_TARGETS`에 더한다. 숫자 사각형은 `GuideOverlay`의 `inkOf`가 글자 획으로 재니 따로 계산하지 않고, 데스크톱과 폰 두 크기를 3배 확대 캡처해 숫자가 가운데인지 본다. 새 요소 첫 판과 보스 판은 가이드가 있는 판이라 둘 다 이 점검을 한다
- 컴포넌트 안에 계산을 쓰지 않는다. 판정, 자리, 색을 정하는 계산은 `frame/`이나 `view/`의 순수 함수로 빼고 테스트를 단다
- 폴더는 역할 하나만 맡는다. 계산 폴더는 모든 파일에 테스트가 있고 화면 폴더는 하나도 없다(`testing.md`). 둘이 섞이기 시작하면 폴더를 나눈다
- 한 파일이 500줄을 넘으면 나눌 때가 된 신호다. 바로 나누지 말고 알린다. `Board.tsx`(514줄)와 `validate.ts`(536줄)를 이렇게 나눴다(2026-10-04, 10-05). `frame/timeFrame.ts`(541줄)는 13월드 연출로 500줄을 넘어 한 수의 길과 구간 시간을 `frame/pathFrame.ts`로 나눴다(2026-10-06). `frame/cellLookFrame.ts`(500줄)는 장치, 사다리, 씨앗, 덩굴 묶음을 요소 파일의 `<요소>LookOf`로 옮겨 344줄로 줄였다(2026-10-07). `frame/iceStoneFrame.ts`(527줄)는 얼음 돌 하나만 다뤄 그대로 둔다(사용자)
- 새 폴더, 새 파일 이름 규칙, 새 접미어는 만들기 전에 사용자에게 묻는다
- 하위 폴더는 `index.ts`가 바깥에 내보내고 폴더 안끼리는 직접 가져온다. 순환 import가 생기면 아래층 파일(`cellRule`, `walkRule`처럼)로 뺀다
- 도우미 함수(`lerp`, `clamp01`, `same` 등)는 새로 만들기 전에 이미 있는지 찾는다
- import는 `@/` 경로 별칭을 쓴다. 같은 폴더 안은 `./`를 허용한다
- 공유 타입은 `game/types.ts`, Props와 작은 로컬 타입은 그 파일 안. 2~3곳 이상 반복되면 공유 타입으로 올린다

## 상수

- 한 파일 안에서 3곳 이상 쓰면 파일 상단 대문자 상수로 분리하고, 1~2곳이면 인라인
- 색은 상수가 아니라 `index.css`의 `@theme` 토큰으로 둔다
- 별도 `constants/` 폴더는 만들지 않는다

## 화면 문구

- 화면에 보이는 문구는 코드에 직접 쓰지 않고 `apps/web/src/i18n/`의 사전에 둔다. **새 문구는 지원하는 여섯 언어에 모두 넣는다.** 스테이지와 월드 이름도 마찬가지다
- **월드를 만들기 전에 그 열 판의 이름을 여섯 언어로 먼저 채운다.** 한두 언어만 채우면 나머지 언어 화면에 영어가 섞여 나온다. `i18n.test.ts`가 빠진 것을 잡는다
- **가이드 문구(`guide.*`)는 있는 문구와 같은 꼴로 쓴다.** 한 단계에 한 문장, 마침표 없이 `~요`로 끝맺고, 한국어 15~38자(가운데값 23자)다. 두 가지를 말해야 하면 `~고`, `~서`, `~면`으로 한 문장에 잇는다(예: "얼음에서는 멈출 때까지 미끄러져요", "덩굴을 밟으면 거기서 자라기를 멈춰요"). 다른 다섯 언어도 한 문장이다. 쓰기 전에 사전의 `guide.` 줄을 다 읽고 맞춘다. 121 `guide.iceStone`을 두 문장으로 썼다가 고쳤다
- `STAGE`, `MOVES` 같은 영어 대문자 라벨은 디자인 요소라 사전에 두지 않는다
- 구조와 빠진 번역 처리는 `docs/ARCHITECTURE.md` "문구와 다국어"를 따른다

## 포맷

- Prettier가 기준이다 (`.prettierrc`). 세미콜론 없음, 작은따옴표, 100자
- import는 외부 라이브러리, 내부 파일, CSS 순서로 그룹 사이에 빈 줄을 둔다. 정렬은 Prettier 플러그인이 한다
- Tailwind 클래스 순서는 Prettier 플러그인이 정렬한다
- 작업을 마치면 `pnpm format`을 실행한다
- 커밋 전 Husky가 lint-staged로 staged 파일에 oxlint와 Prettier를 돌린다. 설정은 루트 `package.json`의 `lint-staged`
- 줄바꿈은 LF로 고정한다 (`.gitattributes`)

## 커밋과 Git

- 브랜치는 `main` 하나, 이슈와 PR 없음
- 커밋 메시지는 prefix(`feat:`, `fix:`, `refactor:`, `chore:`, `test:`, `style:`, `docs:`) + 한 개념으로 뭉뚱그린 한 구절
- 구절은 주석과 같이 명사로 끝맺는다. `~다`, `~ㅁ/~음/~함`, 조사로 끝내지 않는다
- 여러 변경은 나열하지 말고 상위 개념 하나로 일반화한다
- `및`, `/`, `~와`, `~과` 같은 연결자와 `변경`, `수정` 같은 군더더기, `을`/`를` 조사는 뺀다
- 예: `feat: 상자 밀기 규칙`, `fix: 높은 칸 상자 낙하 위치`, `fix: 큐브 출발 순간 그리는 순서` (`fix: 큐브가 상자 앞으로 튀어나옴`이 아니다)
- 커밋은 사용자가 하라고 할 때만 한다. 메시지는 한 줄이고 공동 작성자 줄을 넣지 않는다
